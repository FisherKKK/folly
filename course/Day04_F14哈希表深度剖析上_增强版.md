## 核心内容

### 4.1 F14 命名由来与设计理念

**F14 = Filtering 14 keys**

F14 是 Facebook 开发的高性能哈希表，其核心创新在于使用 SIMD 指令同时过滤 14 个键。

**实际源码证据**（folly/container/detail/F14Table.h:599-604）：

```cpp
// F14 的块容量根据元素大小动态调整
static constexpr unsigned kCapacity = sizeof(Item) == 4 ? 12 : 14;

static constexpr unsigned kDesiredCapacity = kCapacity - 2;

static constexpr unsigned kAllocatedCapacity =
    kCapacity == 12 ? 14 : 15;  // 12 时分配 14，14 时分配 15
```

**关键设计决策**：
- **4字节元素**：容量为 12（4个槽用于控制位），适配 64 字节缓存行
- **其他大小**：容量为 14，最大化利用 16 字节 SIMD 寄存器
- **理论最大负载因子**：12/14 ≈ 85.7%（远超传统哈希表的 50-75%）

**性能数据**（F14 论文与实际测试）：
- **查找命中**：期望探测长度 1.04
- **查找未命中**：期望探测长度 1.275，P99 = 4
- **vs std::unordered_map**：2-4x 更快
- **vs google::dense_hash_map**：内存效率提升 2 倍

### 4.2 数学原理：为什么是 14？

#### 生日悖论的反向应用

传统哈希表使用单槽（1-way），容易发生冲突：
```
房间 23 人，2 人同月同日生日的概率 = 50%
```

F14 使用 14-way chunk，相当于"8人在同一周"的问题：
```
需要 160 人才能让 8 人同一周的概率达到 50%
```

#### 探测长度分析

**实际测量数据**（folly/container/F14.md）：

```
负载因子  查找命中探测长度  查找未命中探测长度  P99
50%       1.00              1.00                1
75%       1.00              1.00                2
85.7%     1.04              1.275               4
```

这意味着在 85.7% 的负载因子下：
- **96% 的查找命中**在第一个 chunk 就找到
- **<1% 的查找**需要探测超过 3 个 chunk

### 4.3 SIMD 向量过滤：深度剖析

#### 标签系统设计

**标签计算**（源码分析）：

```cpp
// folly/container/detail/F14Table.h
// 每个键计算 1 字节标签
// 格式：0xxxxxxx (最高位确保非零)
// 7 位熵提供 128 个不同的标签值

struct F14HashToken {
    uint8_t tag;      // 7 位标签
    size_t index;    // 起始 chunk 索引
};
```

**实际 Chunk 结构**（folly/container/detail/F14Table.h）：

```cpp
template <typename Item>
struct F14Chunk {
    // 16 字节对齐的标签向量（x86-64: SSE2, ARM: NEON）
    alignas(16) uint8_t tags[16];

    // 实际存储的键值对
    Item items[kCapacity];

    // 控制位（根据实现可能内联在 tags 中）
};
```

#### SIMD 过滤实现详解

**x86-64 SSE2 实现**（实际源码模式）：

```cpp
// folly/container/detail/F14Mask.h
template <typename MaskType, typename MaskType2>
FOLLY_ALWAYS_INLINE static constexpr MaskType maskEmpty(
    MaskType mask, MaskType2 fullMask) {
    // 1. 生成空槽掩码
    // 2. 过滤掉已占用的槽
}

// 实际的查找逻辑（简化版）
bool findInChunk(F14Chunk* chunk, uint8_t target_tag, const Key& key) {
    // 1. SIMD 加载：对齐加载 16 字节
    __m128i tag_vector = _mm_load_si128((__m128i*)chunk->tags);

    // 2. 广播目标标签到所有位置
    __m128i target_vec = _mm_set1_epi8(target_tag);

    // 3. 并行比较：生成 16 个比较结果
    __m128i cmp = _mm_cmpeq_epi8(tag_vector, target_vec);

    // 4. 提取掩码：将比较结果转换为 16 位整数
    uint16_t mask = _mm_movemask_epi8(cmp);

    // 5. 应用完整掩码：只保留有效槽位（0-13 或 0-11）
    constexpr uint16_t kFullMask = kCapacity == 12 ? 0x0FFF : 0x3FFF;
    mask &= kFullMask;

    // 6. 快速路径：如果掩码为空，立即返回
    if (FOLLY_UNLIKELY(mask == 0)) {
        return false;
    }

    // 7. 对每个候选槽进行精确比较
    while (mask) {
        // 找到最低设置位（__builtin_ctz = count trailing zeros）
        int slot = __builtin_ctz(mask);

        // 精确键比较
        if (chunk->items[slot].key == key) {
            return true;  // 找到匹配
        }

        // 清除已检查的位
        mask &= (mask - 1);
    }

    return false;
}
```

**ARM NEON 实现**（folly/container/detail/F14IntrinsicsAvailability.h）：

```cpp
#if FOLLY_NEON
// ARM 使用 NEON 指令
#include <arm_neon.h>

// NEON 实现类似但指令不同
uint8x16_t tag_vector = vld1q_u8(chunk->tags);
uint8x16_t target_vec = vdupq_n_u8(target_tag);
uint8x16_t cmp = vceqq_u8(tag_vector, target_vec);

// ARM 缺少 movemask，需要额外处理
uint64x2_t mask64 = vreinterpretq_u64_u8(cmp);
mask = (vgetq_lane_u64(mask64, 0) |
         (vgetq_lane_u64(mask64, 1) >> 16)) & kFullMask;
#endif
```

**性能分析**：
- **SIMD 指令数**：每次过滤只需要 3-5 条 SIMD 指令
- **内存访问**：标签向量只加载一次（16 字节对齐）
- **分支预测**：大多数查找只分支 1 次（命中或第一个候选）

### 4.4 双重哈希探测的数学原理

#### 为什么不用线性探测？

**线性探测的问题**：
```
负载因子   聚类长度    平均探测长度
50%        2-4        1.5
75%        8-16       4.0
87.5%      32-64       16.0（不可接受）
```

**双重哈希的优势**：
```
负载因子   平均探测长度（双重哈希）
85.7%      1.04（命中）/ 1.275（未命中）
```

#### 实际实现细节

**源码分析**（folly/container/detail/F14Table.h）：

```cpp
// 双重哈希使用黄金比例常数
// 这个常数能提供良好的分布特性

template <typename Key>
class F14HashPolicy {
    // 第一哈希：标准哈希函数
    static size_t hash1(const Key& key) {
        return std::hash<Key>{}(key);
    }

    // 第二哈希：使用黄金比例混合
    // 0x9e3779b97f4a7c15 是 2^64 / φ（黄金比例）的整数部分
    static size_t hash2(const Key& key, size_t shift) {
        return hash1(key) * 0x9e3779b97f4a7c15ULL >> shift;
    }

    // 探测序列
    static size_t probe_index(
        size_t h1, size_t h2,
        size_t chunkIndex,
        size_t scaleBits) {
        // h1：主哈希值
        // h2：步长
        // chunkIndex：当前探测序号
        // scaleBits：容量缩放位数

        // 探测公式：h1 + chunkIndex * h2
        return (h1 + chunkIndex * h2) >> scaleBits;
    }
};
```

**关键优化**：
1. **黄金比例常数**：确保探测序列均匀分布
2. **位移而非模运算**：避免昂贵的除法指令
3. **缩放位数**：适应不同大小的哈希表

### 4.5 溢出计数：引用计数墓碑

#### 问题描述

**传统探测哈希表的墓碑问题**：

```cpp
// 场景：插入 A, B, C，删除 B，再查找 C
Chunk: [A, TOMBSTONE, C, ... ]

// 问题：探测 C 时必须跳过 TOMBSTONE
// 但如果大量删除，会形成"墓碑链"
```

**F14 的解决方案**（folly/container/F14.md）：

```cpp
struct Chunk {
    uint8_t tags[16];  // 标签数组

    // 每个槽可以有 3 种状态：
    // 1. 空槽：tag = 0
    // 2. 已占用：tag = 计算出的 7 位标签
    // 3. 溢出：tag 最高位 = 1（记录此块溢出的键数量）

    // 额外的溢出计数器（某些实现）
    uint8_t chunk_overflow_count;
};
```

**工作原理**：

```
插入流程：
1. 计算键的哈希值和标签
2. 找到目标 chunk
3. 如果 chunk 已满：
   a. 增加所有探测过的 chunk 的溢出计数
   b. 继续探测到下一个 chunk
4. 插入键值对

删除流程：
1. 找到键所在槽位
2. 清空槽位（tag = 0）
3. 递减沿途所有 chunk 的溢出计数

探测优化：
- 如果溢出计数 = 0，可以提前停止探测
- 这自动实现了"墓碑"的效果，但无需额外存储
```

**优势对比**：

| 特性 | 传统墓碑 | F14 溢出计数 |
|------|-----------|--------------|
| 存储开销 | 每个槽 1 字节 | 共享计数器 |
| 清理策略 | 周期性重哈希 | 自动递减 |
| 提前退出 | 不支持 | 支持（溢出=0） |
| 额外探测 | 不可避免 | 大幅减少 |

## 研究性深入：SIMD 的数学原理

### 为什么是 16 字节对齐？

**缓存行分析**：

```
CPU 缓存行大小：64 字节
SIMD 寄存器大小：16 字节（SSE2/NEON）

16 字节块的优势：
1. 正好是一个 SIMD 寄存器的大小
2. 4 个块 = 64 字节 = 1 个缓存行
3. 标签向量（16 字节）+ 14 个键值对 ≈ 256 字节 = 4 个缓存行

内存布局：
[Tag 16B][Control][Item0][Item1]...[Item13]  <- 连续内存
   ↓
  一个或少数几个缓存行覆盖
```

### SIMD 指令的功耗分析

**现代 CPU 的 SIMD 能效**：

```
指令类型        延迟    吞吐量    功耗
标量比较        1       1         基准
SSE2 cmpeq     1       0.5       1.2x
AVX2 cmpeq     1       0.25      1.5x

结论：SIMD 在相同能耗下提供 2-4x 性能
```

## 常见陷阱与最佳实践

### ❌ 错误用法

```cpp
// 1. 不预分配容量
folly::F14FastMap<std::string, int> map;
for (int i = 0; i < 10000; ++i) {
    map[std::to_string(i)] = i;  // 触发多次重哈希！
}

// 2. 使用大对象作为键
struct BigKey {
    char data[1024];
};
folly::F14FastMap<BigKey, int> map;  // 应该用 F14NodeMap

// 3. 忽略异构查找
std::string key = "hello";
map.find(key);  // 构造临时 std::string
```

### ✅ 正确用法

```cpp
// 1. 预分配容量
folly::F14FastMap<std::string, int> map;
map.reserve(10000);

// 2. 选择正确的类型
using TransparentHash = folly::transparent<folly::Hasher<folly::StringPiece>>;
folly::F14FastMap<std::string, int, TransparentHash> map;

// 3. 使用异构查找
folly::StringPiece key = "hello";
map.find(key);  // 零拷贝查找
```
